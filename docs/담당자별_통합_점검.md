# 담당자별 통합 점검 및 남은 작업

2026-11-03 통합 코드 기준이다. 브랜치 병합·자동 테스트 통과와 실제 서비스 데이터 연결 완료는 구분한다. 실제 키·사용자 토큰·공식 자료·기기가 필요한 작업은 완료로 표시하지 않는다.

## 현재 반영된 기능

- 회원·그룹·날씨·체크리스트·관리자와 전체 39개 테이블 migration.
- 위치 동의/철회·GPS 최신 한 건, 관심지역 CRUD·소유권·5개 제한.
- 지진·특보·재난문자·지진대피소 수집기, 원문 수정 이력·수집 잠금·임대·실패 복구.
- 대피소 PostgreSQL/PostGIS 저장소와 수집기의 동일 원본 키·UUID.
- 프런트 지도·경로·웹 Google/Kakao 인가 코드 로그인, 백엔드 코드 교환과 기존 토큰 검증.
- 대시보드·재난 목록/상세·AI 요약/채팅·알림 9개 HTTP API. 명시적 설정 시 활성화되며 기본값은 OFF다.
- FCM 발송·암호화·인증·알림 부분 변경과 발송 결과 분류. 실제 기기 수신까지 확인한 상태는 아니다.

## 1. 본인 담당 및 공통 실행

| 순서 | 할 일 | 완료 기준 |
|---|---|---|
| 1 | 새 빌드로 서버 실행, 실제 DB 비밀번호·Flyway 상태 확인 | 실제 서버가 DB에 접속하고 보호 API가 미인증 401 |
| 2 | Google 웹 클라이언트 ID·Secret, Kakao REST API 키·Secret·숫자 앱 ID, 정확한 Redirect URI 설정 | 실제 Google/Kakao 사용자 로그인과 회원 조회 성공 |
| 3 | 로그인 갱신·로그아웃·탈퇴·복구, 그룹 생성/가입/이관, 체크리스트, OPS 기능을 앱과 연결 | 실제 두 계정·앱 재시작·권한 변경 후에도 서버 상태와 일치 |
| 4 | 아래 HTTP 활성화 설정을 적용하고 보호 경로 검증 | 관심지역과 새 9개 API 모두 세션 인증 적용, 인증 Bean 하나 |

웹 코드 교환은 `GOOGLE_WEB_CLIENT_ID`(또는 기존 ID), `GOOGLE_CLIENT_SECRET`, `KAKAO_REST_API_KEY`, `KAKAO_CLIENT_SECRET`가 필요하다. 검증용 `GOOGLE_CLIENT_IDS` 및 `KAKAO_APP_ID`도 맞춰야 한다. 프런트의 Kakao 웹 인가 코드 방식에는 JS 키가 아닌 REST API 키를 사용한다.

```dotenv
eodiisseo.owned-http.enabled=true
AUTH_BRIDGES_ENABLED=true
```

HTTP 경로 활성화는 운영 데이터 연결 완료를 의미하지 않는다. 없는 자료/구현 때문에 의존성 오류가 나면 해당 작업을 연결해야 하며 임의 응답으로 숨기지 않는다.

## 2. 본인 담당 위치·재난·수집 및 DB

| 우선순위 | 할 일 | 완료 기준 |
|---|---|---|
| P0 | 확보한 공식 시군구 SHP의 원본 좌표계·자료 기준년도 확인, WGS84 변환·실지역 적재 | 공식 코드·경계·출처로 관심지역과 좌표 지역을 해석 가능 |
| P0 | 공식 영향지역 코드/경계와 재난 상태·심각도 계약 연결 | 진앙/문자 수신지역을 피해범위로 바꾸지 않고 실제 근거로 판정 |
| 완료 | `DashboardDisasterQueryReader` DB 공급자, 진행 재난 기본 목록·발생시각 정렬·단일 원문·수집 상태 연결 | 공식 원문과 실제 수집 이력 사용, 최신성 미확인 목록은 성공으로 위장하지 않음 |
| P1 | AI 원문 버전 조회·현재 버전·실제 종료시각의 읽기 계약 제공 | 요약이 검증된 단일 원문 revision을 사용 |
| 검증 완료 | 네 제공처의 전체 페이지→worker→격리 DB 저장 확인 | 지진 0건·특보 19건·재난문자 24건·대피소 8,192건(2026-11-03 조회 시점), 실제 서비스 DB 적재와 구분 |
| P1 | 미구현 나머지 외부 API 및 지진 정정/후속 발표의 사건 통합 규칙 구현 | 제공자 계약을 검증하고 원문·사건 중복을 구분 |

공식 경계 원본은 `backend/build/reference/admin-areas`에 있고 Git에서는 제외한다. PRJ와 기준년도 미확인 상태이므로 운영 DB에는 아직 적재하지 않았다. 수집기 네 종류는 전체 페이지의 실응답과 격리 DB 저장을 확인했다. 실제 날씨 조회도 별도로 통과했다. 이 사실을 실제 서비스 DB의 전국 자료 적재 완료로 보고하지 않는다.

worker는 `COLLECTION_WORKER_ENABLED=true` 후 실행된다. 재난 변경 후 알림/요약을 시작하는 커밋 이후 이벤트·실행 연결도 필요하다. 수집 중간의 불완전 데이터를 발송 트리거로 사용하지 않는다.

## 3. 프런트 담당

- 실제 웹 로그인·팝업 취소·실패·탈퇴 대기 상태를 기기/브라우저에서 검증한다. 플랫폼 콘솔의 Redirect URI와 프런트가 생성하는 URI를 정확히 맞춘다.
- 현재 웹 세션은 메모리에만 저장한다. 새로고침 복원 정책, 안전한 저장, refresh 회전·동시 401 단일 갱신·서버 로그아웃/탈퇴를 구현한다.
- 그룹·체크리스트·위치 동의·관심지역·재난·대시보드·알림·OPS 화면의 mock/로컬 상태를 실제 API에 연결한다.
- 지도·장소 검색·경로 화면을 백엔드 대피소 ID·거리/시간 단위·보호 API와 맞춘다. 웹 TMAP 공개 키의 도메인 제한과 서버 키 구분을 확인한다.
- 네이티브 소셜 로그인은 아직 별도 작업이다. 앱 패키지/Bundle ID는 등록됐지만 실제 서명 SHA-1/키 해시·SDK·기기 빌드 연결을 확인해야 한다.

## 4. AI·대시보드 담당

- HTTP Controller는 구현됐다. 위치·재난·원문 Port 연결을 본인 담당과 맞춘다. 목록/상세 기본 정책 미확정을 빈 정상 응답으로 우회하지 않는다.
- 실제 공식 행동요령 본문과 승인 공급자, 개인정보 외부 전송 정책·보존 정책을 연결한다. 체크리스트 seed의 안내문은 RAG corpus가 아니다.
- Ollama 모델/환경과 실제 요약·질문 정답셋으로 결과·근거·정보 부족·폐기 원문을 검증한다.
- 요약 작업 실행기·재시도·현재 원문 버전 검사·실제 endedAt 기반 보존 처리를 연결한다.

## 5. 알림 FCM 담당

- Firebase 서비스 계정, AES-GCM 키 파일, 실제 기기 토큰과 권한을 설정한다. 필요한 persistence/crypto/FCM 플래그는 각각 명시적으로 활성화한다.
- 실제 재난 변경 이벤트와 발송 실행 지점, 재시도 예산·야간 시간 정책을 연결한다.
- 앱에서 토큰 등록→수신→설정 OFF→지역 해제→탈퇴를 실기기로 확인한다. 중복/미확정 발송은 무조건 재시도하지 않는다.
- `AUTH_BRIDGES_ENABLED=true`이면 공통 인증 구현이 우선한다. 두 인증 구현을 동시에 생성하지 않는다.

## 6. 대피소·경로 담당

- DB 전환은 반영됐다. 실제 주변 조회→수집기 갱신→서버 재시작→상세→경로를 같은 ID로 확인한다.
- 관심지역 기준 조회·회원 소유권 검증, DB 기반 회원당 분당 경로 10회 제한은 구현됐다. 실제 관심지역 중심 좌표 적재 후 앱에서 확인한다.
- TMAP 경로 실패·경로 없음·잘못된 좌표·호출 한도·대피소 미사용 전환을 검증한다. 추천 경로가 재난 안전을 보장한다고 표시하지 않는다.

## 7. 배포·팀 전체

- 서버 PostgreSQL/PostGIS 설치·DB/계정/권한·TLS·migration 실행·백업/복구 절차를 구성한다. 현재 PowerShell 설치 스크립트는 로컬 Windows용이다.
- 통합 브랜치 CI와 격리 DB migration·HTTP 검증을 구성한다. 기본 test 프로필 성공만으로 운영 Bean 기동을 판단하지 않는다.
- 실계정 로그인→위치/관심지역→실재난/날씨→대피소/경로→그룹/체크리스트→실제 알림→OPS 수집→로그아웃/탈퇴 순서로 통합 시나리오를 완료한다.
- 검증 결과와 남은 제약을 확인한 뒤 develop PR을 만든다. 이번 작업은 integration/backend-develop 통합이며 develop/main으로 배포하지 않는다.
